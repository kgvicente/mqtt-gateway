MQTT Gateway / Referencia de Integración

Conecta tu bróker MQTT con tu backend

Especificación contractual de endpoints HTTP requeridos para delegar la autenticación de clientes MQTT, la autorización de tópicos y el sondeo continuo de disponibilidad.

MQTT Gateway actúa como un proxy inverso de alta velocidad y baja latencia que desacopla EMQX, Mosquitto, VerneMQ y otros brókers de los sistemas y microservicios de backend (IoT Core Service, Device Gateway, Telemetry Service y servicios futuros). Cuando un cliente MQTT se conecta o intenta publicar/suscribirse, el gateway enruta la decisión al backend correspondiente.

Esta documentación es pública y accesible en /gateway/docs sin necesidad de credenciales ni token administrativo.

Cabeceras estándar en solicitudes salientes

Cabecera Tipo Requerida Descripción
Content-Type String Obligatoria Valor fijo application/json. El payload de la solicitud siempre es un objeto JSON.
X-EMQX-API-KEY String Si está configurada Clave secreta compartida entre el gateway y el backend. No se envía si el backend fue registrado sin clave.

Seguridad y Red: Todos los endpoints de backend deben responder dentro del límite estricto de timeout configurado (2 000 ms predeterminado). Si un backend excede este tiempo o responde un código de error, el gateway denegará el acceso por seguridad de red (criterio fail-closed).

Adaptadores MQTT

Todos los endpoints utilizan POST. Las rutas se muestran completas; /api/v1/gateway/auth y /api/v1/gateway/acl conservan el formato EMQX. Los apartados de backend que siguen describen el contrato saliente compartido.

BrókerAutenticaciónAutorización
EMQX/api/v1/gateway/emqx/auth/api/v1/gateway/emqx/acl
Mosquitto/api/v1/gateway/mosquitto/auth/api/v1/gateway/mosquitto/acl
VerneMQ/api/v1/gateway/vernemq/auth/api/v1/gateway/vernemq/acl
Genérico/api/v1/gateway/generic/auth/api/v1/gateway/generic/acl

EMQX y Genérico

Enviar Content-Type: application/json. Auth recibe {"clientid":"device_sensor_01","username":"usuario","password":"clave"}. ACL recibe {"clientid":"device_sensor_01","username":"usuario","topic":"devices/telemetry","action":"publish"}; para suscripciones, action es subscribe. Configurar el cuerpo HTTP de EMQX con estas propiedades y apuntar a las rutas /emqx/auth y /emqx/acl. EMQX recibe HTTP 200 con {"result":"allow"}, {"result":"deny"} o {"result":"ignore"}. En allow se conserva is_superuser. Genérico recibe HTTP 200 con {"allowed":true,"status":"allow"}, {"allowed":false,"status":"deny"} o {"allowed":false,"status":"ignore"}.

Mosquitto con mosquitto-go-auth

Configurar el backend HTTP del complemento: auth_opt_backends http, auth_opt_http_host 127.0.0.1, auth_opt_http_port 8085, auth_opt_http_getuser_uri /api/v1/gateway/mosquitto/auth, auth_opt_http_aclcheck_uri /api/v1/gateway/mosquitto/acl, auth_opt_http_method POST, auth_opt_http_params_mode json y auth_opt_http_response_mode status. La ruta del complemento nativo auth_plugin depende de la instalación de Mosquitto.

Auth recibe {"clientid":"device_sensor_01","username":"usuario","password":"clave"}. ACL recibe {"clientid":"device_sensor_01","username":"usuario","topic":"devices/telemetry","acc":2}. acc=2 se traduce a publish; acc=1 y acc=4 a subscribe. Otros valores se deniegan. Se admiten JSON y formularios application/x-www-form-urlencoded con esos mismos campos. Respuesta: HTTP 200 para allow, 400 para deny y 404 para ignore, con result en JSON para diagnóstico. En modo status el complemento interpreta tanto 400 como 404 como un resultado no permitido; la cadena de backends del bróker determina si se prueban otros proveedores.

VerneMQ con vmq_webhooks

Activar plugins.vmq_webhooks = on. Registrar tres webhooks: auth_on_register apunta a /api/v1/gateway/vernemq/auth; auth_on_publish y auth_on_subscribe apuntan a /api/v1/gateway/vernemq/acl. Para cada webhook configurar vmq_webhooks.<nombre>.hook y vmq_webhooks.<nombre>.endpoint con el hook y la URL completa. Se admiten también los nombres de esos tres hooks terminados en _m5 para MQTT 5.

El complemento envía JSON y la cabecera vernemq-hook. Auth recibe {"client_id":"device_sensor_01","username":"usuario","password":"clave"}. Publicación recibe {"client_id":"device_sensor_01","username":"usuario","topic":"devices/telemetry","qos":1}. Suscripción recibe {"client_id":"device_sensor_01","username":"usuario","topics":[{"topic":"devices/telemetry","qos":1}]}. client_id se copia a clientid; el hook de publicación añade action=publish y cada entrada de topics añade action=subscribe. Cada tópico tiene resolución, métrica y auditoría propias. Todos deben devolver allow: un deny deniega el conjunto; sin deny, un ignore produce next. Una lista vacía o inválida se deniega. Las respuestas usan HTTP 200: {"result":"ok"} para allow, {"result":{"error":"not_allowed"}} para deny y {"result":"next"} para ignore. No se devuelven modificadores de tópicos ni privilegios de superusuario específicos de VerneMQ.

Contrato saliente compartido

Los adaptadores traducen entrada y respuesta; los backends HTTP continúan recibiendo el contrato JSON existente (clientid, username, password para auth; clientid, username, topic, action para ACL). Se conservan campos adicionales, incluyendo los originales del bróker. Los backends responden con HTTP 2xx y result=allow|deny|ignore. La selección sigue siendo por prefijo de clientid para auth y de topic para ACL. JSON inválido, timeout y fallo del backend producen deny. Los privilegios de superusuario siguen siendo exclusivos del formato EMQX; en los otros brókers la autorización ACL se evalúa por separado.

Referencias del protocolo: mosquitto-go-auth y webhooks de VerneMQ.

Acceso autónomo al panel

La configuración está bajo gateway.admin en application.yml:

Propiedad en gateway.adminVariable de entornoValor por defecto
auth-providerGATEWAY_ADMIN_AUTH_PROVIDERinternal
usernameGATEWAY_ADMIN_USERNAMEadmin
passwordGATEWAY_ADMIN_PASSWORDadmin-secret-2026$

En modo internal, POST /api/admin/auth/login recibe {"username":"admin","password":"<contraseña configurada>"} y devuelve {"token":"<UUID aleatorio>","username":"admin"}. Credenciales incorrectas: HTTP 401; campos vacíos: HTTP 400. El token se conserva únicamente en memoria y caduca ocho horas después de su emisión, sin renovación por actividad. Se pueden emitir varias sesiones. Reiniciar invalida todas las sesiones. Las entradas caducadas se eliminan al verificarlas y en cada login exitoso.

Todas las operaciones administrativas protegidas y GET/POST /api/admin/auth/verify requieren Authorization: Bearer <token>. La verificación correcta devuelve {"valid":true}; un token ausente, desconocido o caducado devuelve HTTP 401. El panel sigue funcionando si EMQX está detenido. Configurar GATEWAY_ADMIN_PASSWORD en el entorno del servicio para sustituir la contraseña inicial.

En modo emqx, login delega en POST /api/v5/login y cada verificación delega en GET /api/v5/users del Dashboard indicado por GATEWAY_EMQX_URL. Los tokens internos no sirven en modo EMQX, ni los de EMQX en modo interno. No hay cambio automático de proveedor ante un fallo de EMQX. La integración existente por fragmento, almacenamiento e iframe continúa siempre que el token corresponda al proveedor configurado. Salir del panel elimina su sesión del navegador; el token interno sigue vigente hasta caducar o reiniciar. No se añade un endpoint de revocación.

Autenticación de Clientes

POST /auth

Invocado por el gateway al recibir una solicitud de conexión MQTT (paquete CONNECT). El servicio de backend debe validar el identificador de cliente y sus credenciales.

Parámetros del cuerpo de la solicitud (JSON)

Campo Tipo Requerido Descripción
clientid String Sí Identificador único del cliente MQTT (ejemplo: cliente-alerta-104).
username String Sí Nombre de usuario presentado en la conexión MQTT.
password String Sí Contraseña presentada en la conexión MQTT. Tratar siempre como información confidencial.

Parámetros de respuesta esperada (JSON)

Campo Tipo Requerido Valores admitidos y significado
result String (Enum) Sí allow para autorizar la conexión del cliente; deny para rechazarla.
is_superuser Boolean Opcional true otorga privilegios de superusuario en el broker EMQX. Por defecto es false.

El backend debe retornar código HTTP 200 OK con el objeto JSON {"result":"allow"} o {"result":"deny"}. La decisión de autenticación se expresa formalmente en el campo result.

Autorización de Tópicos (ACL)

POST /acl

Invocado por el gateway cuando un cliente conectado intenta publicar un mensaje o suscribirse a un tópico MQTT.

Parámetros del cuerpo de la solicitud (JSON)

Campo Tipo Requerido Descripción
clientid String Sí Identificador del cliente MQTT solicitante.
username String Sí Nombre de usuario del cliente MQTT autenticado.
topic String Sí Tópico MQTT objeto de la acción (ejemplo: sensores/panico/sector2).
action String (Enum) Sí Acción solicitada: publish (publicar) o subscribe (suscribirse).

Parámetros de respuesta esperada (JSON)

Campo Tipo Requerido Valores admitidos y significado
result String (Enum) Sí allow para permitir la acción; deny para denegarla; ignore para omitir la regla.

El backend debe retornar código HTTP 200 OK con el objeto JSON {"result":"allow"} o {"result":"deny"}.

Sondeo de Salud y Disponibilidad

GET /health

Endpoint de sondeo continuo consultado automáticamente por el gateway para verificar la vitalidad del servicio, calcular el tiempo de actividad (uptime) y graficar el historial de sondeos en el panel administrativo.

Elemento Tipo Requerido Descripción
Cuerpo de solicitud Sin cuerpo No La petición es un GET sin payload.
Parámetros Ninguno No No requiere parámetros en la URL ni query string.
Cabecera X-EMQX-API-KEY String Opcional El gateway incluye la clave configurada si el backend la tiene establecida.
Respuesta esperada Estado HTTP Sí Códigos HTTP 2xx indican servicio en óptimas condiciones. Códigos 4xx indican servicio accesible con control de acceso. Códigos 5xx indican falla interna en el backend.

El intervalo regular de sondeo es de 30 segundos, con un timeout máximo de 2 000 ms. La operación debe ser rápida, de solo lectura y no ejecutar escrituras pesadas en base de datos.

Seguridad y Cabecera X-EMQX-API-KEY

Para proteger los endpoints de autenticación y autorización frente a accesos no autorizados en la red interna, el gateway soporta una clave secreta compartida transmitida en la cabecera HTTP X-EMQX-API-KEY.

Recomendación Buenas prácticas de integración
Transporte Seguro Utilizar siempre HTTPS en entornos productivos para proteger la clave frente a interceptación.
Validación Estricta El backend debe verificar que el valor recibido en X-EMQX-API-KEY coincida de forma exacta y en tiempo constante con la clave configurada.
Aislamiento de Tokens La clave X-EMQX-API-KEY es exclusiva entre el gateway y el backend. Nunca debe reutilizarse el token Bearer administrativo ni credenciales de usuario final.

Códigos de Error y Resiliencia

El gateway aplica una política estricta de seguridad ante fallos de backend (criterio fail-closed). La siguiente tabla detalla cómo procesa el gateway cada estado de respuesta:

Respuesta del Backend Interpretación del Gateway Acción sobre el Cliente MQTT
HTTP 200 con {"result":"allow"} Aprobación exitosa Acceso permitido.
HTTP 200 con {"result":"deny"} Denegación formal por política del backend Acceso rechazado de inmediato.
HTTP 4xx (400, 401, 403, 404) Solicitud inválida o autorización rechazada en el backend Acceso denegado (fallo registrado en auditoría).
HTTP 5xx (500, 502, 503, 504) Falla interna en el backend Acceso denegado. Se registra incidente si persiste.
Timeout (> 2 000 ms) o conexión rehusada Servicio no disponible o saturado Acceso denegado inmediatamente tras el tiempo límite.
