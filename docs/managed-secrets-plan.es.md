## Contrato final

- Un único modo operativo: claves de backend y token Telegram administrados desde el panel y cifrados en SQLite. No selector de origen ni fallback permanente a variables de entorno.
- YAML/entorno mantienen configuración de proceso y credenciales administrativas de arranque. `GATEWAY_MASTER_KEY` es obligatoria: Base64 estándar de exactamente 32 bytes aleatorios. Sin valor predeterminado ni generación automática en cada arranque. Clave ausente/malformada impide iniciar con error saneado. Cambiarla sin recifrar no es rotación y debe rechazarse. Respaldarla fuera de la DB; pérdida de clave impide recuperar secretos cifrados.
- AES-256-GCM mediante JCA estándar (`AES/GCM/NoPadding`), nonce nuevo de 12 bytes de SecureRandom por cifrado, tag 128 bits y AAD que identifica versión y propietario (`backend:<id>` o `telegram:bot-token`). Envelope versionado. Autenticar formato, longitudes y propietario; modificación o intercambio de filas debe fallar. No almacenar la clave maestra ni un derivado utilizable para descifrar en SQLite. Canary cifrado de valor fijo para detectar clave incorrecta aun sin otros secretos. Verificar todos los secretos al arrancar antes de publicar caché.
- V4 nueva y transaccional; V1/V2/V3 inmutables. Preferir tabla dedicada de secretos separada de rutas/settings/outbox; respuestas API/SSE/exportaciones/checkpoints no incluyen ciphertext, nonce, token ni claves. Un escritor SQLite; cifrado y esperas SQL fuera de metricsLock. Caché publicada después del commit, junto con metadatos coherentes.
- `routes.apiKey` es write-only: string no vacío reemplaza, omitido conserva y `""` elimina explícitamente. `null` y tipos no string se rechazan con 400. Límite razonable documentado (4096 caracteres), clave válida para cabecera HTTP, sin CR/LF/control. GET responde únicamente `hasApiKey` y metadatos públicos; eliminar `apiKeyEnv`/`apiKeyEnvMissing` de contrato de uso cotidiano. `apiKeyEnv` nuevo no vacío se rechaza con guía de actualización; no mantener segundo modo. No devolver el secreto ni en create/PUT. Borrar backend elimina su secreto en la misma transacción.
- `settings.telegram.botToken` es write-only, con igual regla de omisión/contenido/`""`/null. GET mantiene `tokenConfigured` como existencia del token guardado. Guardar token+chat+enabled en una operación debe funcionar; eliminar token exige desactivar en esa misma operación o retorna 400 sin cambios. Un PUT solo de monitoreo conserva todo Telegram y viceversa; toda petición mixta es atómica.
- Formulario de edición siempre vacío para secretos; conservar por omisión. Acciones explícitas para reemplazar/eliminar. Nunca colocar secreto existente en value, atributos, HTML, consola, localStorage/sessionStorage, URLs o mensajes de error. Mostrar presencia y ayuda. Backend nuevo permite clave opcional. Botón prueba conserva semántica 202/cola; no habilitar token real automáticamente.
- Se cargan secretos descifrados en caché privada de proceso. Auth/ACL y probes usan la caché, sin SQL ni descifrado por petición. Actualizar secreto cambia siguientes llamadas sin reiniciar; las ya enviadas pueden completar con la credencial anterior. Invalidar generación de sondeos al cambiar la clave para descartar respuestas antiguas y reiniciar rachas; cambios solo de metadatos conservan rachas. Token nuevo se usa en futuros intentos del worker; no persistir token en outbox.
- Errores saneados: no registrar valores secretos, cuerpos de proveedor, URLs con token ni excepciones de criptografía que incluyan entradas. No campos arbitrarios en settings para esconder secretos. Operaciones administrativas mantienen autenticación existente.
- Validación antes de persistir: las claves HTTP rechazan controles, DEL, caracteres incompatibles con la cabecera y valores compuestos solo por espacios. El token acepta caracteres de segmento seguros (`A-Z`, `a-z`, dígitos, `:`, `_`, `-`), sin consultar al proveedor para validarlo. `hasApiKey` y `tokenConfigured` indican presencia, no validez ante el servicio externo.

## Migración

- Importar una sola vez las referencias existentes api_key_env resolviendo su valor y el antiguo token de entorno si existe. Requiere clave maestra válida. Preparar todo antes del commit: si falta una referencia necesaria, abortar con ID/nombre de variable, sin valores y sin migración parcial. Importar también filas pausadas con referencias; no descartar credenciales silenciosamente.
- En una transacción: secretos cifrados + canary + limpieza de referencias persistidas + marcador de importación. En reinicios posteriores el entorno legado no sobreescribe cambios del panel ni resucita secretos eliminados. Nuevos arranques no adquieren un modo externo permanente.
- Conservar importación JSON anterior y siembra inicial sin escribir valores legibles de secretos en SQLite. Datos y archivos legados no se borran; documentar backups antiguos que pueden contener secretos. Coordinar contratos exactos con QA antes de cambios.
- Migraciones son de avance; un binario anterior no acepta V4. Rollback usa respaldo completo previo con servicio detenido. No tocar DB de preview en pruebas. Root respalda volumen antes de actualizar demo.
