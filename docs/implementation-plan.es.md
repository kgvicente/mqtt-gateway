## Fase 2: monitoreo

Contrato de coordinación F2: `GET /api/admin/settings` devuelve `{monitoring:{...}}`; PUT valida los cuatro valores globales del objeto monitoring y conserva futuras secciones omitidas. Ruta.monitoring omitido en PUT conserva overrides; objeto proporcionado reemplaza sus overrides, y null/omitido por campo hereda. Respuesta de ruta añade effectiveMonitoring. Métricas añaden consecutiveFailures, consecutiveSuccesses, pendingState (null/failure/recovery) y awaitingObservation; status conserva los valores públicos existentes y refleja estado confirmado. Sondeo manual devuelve 409 si otro ocupa el slot, sin cambiar historial automático, uptime, contadores ni incidentes. Tras reiniciar, status Unknown hasta observar; un incidente abierto se conserva y exige recoveryThreshold para cerrarse. Sin incidente previo, primer éxito inicial confirma salud sin emitir recuperación. En tests que usan intervalo 1s, configurar timeout de sondeo 500ms y umbrales 1/1; timeout auth/ACL sigue 2000ms. No recortar valores inválidos silenciosamente.

- GET/PUT /api/admin/settings protegidos. Settings globales `monitoring`: probeIntervalSeconds=30, probeTimeoutMs=2000, failureThreshold=3, recoveryThreshold=2. En migración preservar intervalo/timeout previamente configurados; activar umbrales 3/2. YAML inicializa, DB manda después.
- Ruta tiene `monitoring` overrides, campos null/omitidos heredan, respuesta incluye `effectiveMonitoring`. PUT ruta conserva overrides si el objeto completo se omite; campos null dentro de objeto eliminan override. Validar intervalos 1..86400 s, timeout 100..60000 ms y menor al intervalo efectivo, umbrales 1..100; rechazar global si invalida rutas, informar IDs.
- Timeout auth/ACL sigue independiente. Scheduler por backend fixed-delay desde fin de sondeo; no solapamientos, incluyendo pruebas manuales. Reprogramar en cambios. Generación de configuración invalida resultados en vuelo de rutas pausadas/editadas/eliminadas. Concurrencia acotada por una ejecución por backend.
- Solo sondeos automáticos abren/cierran incidentes. HTTP<500 sano (mantener contrato 4xx); timeout/conexión/5xx fallo. Fallos/éxitos consecutivos, contrario reinicia secuencia. Fechas usan primera muestra de secuencia confirmada. Solo intervalos observados cuentan en uptime.
- Reinicio preserva incidente abierto; contadores consecutivos reinician y estado queda pendiente de observación. Cambio de política reinicia contadores sin cerrar incidente abierto. Pausa/borrado cierre administrativo con motivo. Prueba manual informa sin cambiar secuencias ni incidentes.
- Errores auth/ACL solo métricas/auditoría, no modifican disponibilidad confirmada por sondeo. Exponer contadores pendientes/estado confirmado y settings en SSE.
- Panel ajustes globales, overrides por backend, valor efectivo/herencia, latencia aproximada de detección, accesibilidad/móvil sin rediseño general.

## Fase 3: Telegram

Contrato de implementación F3: `telegram.enabled` global es interruptor maestro; una ruta no puede reactivarlo si está apagado. Ruta `enabled:null` hereda, `false` excluye, `true` participa cuando el global está habilitado. `chatId:null` hereda destino global. Omisión de una sección en PUT conserva su valor; objeto de overrides de ruta reemplaza sus campos. GET settings añade `telegram:{enabled,chatId,tokenConfigured}`; tokenConfigured es informativo, nunca contiene el token. PUT solo modifica enabled/chatId. El botón de prueba requiere configuración efectiva habilitada, token y destino; no acepta texto ni destinos arbitrarios. Un token ausente al reiniciar no debe impedir las funciones principales del gateway: el notificador permanece suspendido y el panel informa tokenConfigured=false. Una nueva activación sin token/destino se rechaza con 400.

Historial: respuesta `{items,total,limit,offset,summary}`; summary incluye conteos por estado y oldestPendingAt. Cada entrega expone id, backendId, incidentId, type, chatId, status, attempts, createdAt, nextAttemptAt, sentAt y lastError saneado. POST prueba devuelve 202 `{id,status}`; esto confirma encolado. El orden por chat usa secuencia de inserción, no comparación de textos ISO. Un chat en espera de retry no bloquea otros chats. Destinos y contenidos se congelan al encolar.

Implementación crítica: bajo routeLock revalidar generación y preparar transición; ninguna espera SQL bajo metricsLock. Persistir incidente y outbox de forma síncrona en una única transacción fuera de metricsLock, luego publicar solo los campos de monitoreo e incidente, preservando contadores de tráfico concurrentes. Un fallo SQL no publica transición definitiva. Writer no adquiere locks de GatewayState. Iniciar worker después de inicializar almacenamiento y cachés; detenerlo antes de cerrar writer. HTTP siempre fuera de transacción. Finalizar entregas condicionalmente al estado sending para no sobrescribir cancelaciones concurrentes. Las cancelaciones no pueden deshacer una petición ya aceptada por Telegram.

Pruebas usan transporte/endpoint inyectable exclusivamente bajo perfil test, reloj controlable en Java y credenciales ficticias. No añadir endpoints públicos para manipular reloj/cola. La configuración de endpoint de prueba debe funcionar en el artefacto que QA realmente ejecuta y rechazarse o ignorarse en producción. Validar respuesta JSON `ok`, errores 429/retry_after, errores HTTP y respuesta malformada sin almacenar cuerpo/URL/excepción que pudiera contener el token. Mensaje de texto plano limitado a 4096 caracteres; sin parse_mode. Mantener aplicación desactivada por defecto y sin envíos reales durante QA.

- Token solo gateway.telegram.bot-token=${GATEWAY_TELEGRAM_BOT_TOKEN:}; no API para token. Telegram HTTP oficial sin SDK, cliente inyectable para pruebas (endpoint externo real fijo en producción; mock configurable solo mediante perfil de test).
- Settings.telegram {enabled:false, chatId:null}; ruta.telegram {enabled:null,chatId:null}, null hereda; effectiveTelegram expuesto. Sin destino/token al activar -> 400. Token nunca en DB/log/errores (URL Telegram contiene token: sanear excepciones).
- GET /api/admin/notifications?limit=...&offset=... (limit default25/max100), POST /api/admin/notifications/test body {backendId?:...}. Test usa únicamente destino ya configurado, persiste entrega con type=test, devuelve 202/id, requiere autenticación. Nuevos eventos solo desde activación, no retroactivos.
- Outbox y transición de incidente misma transacción. Snapshot de destinatario/contenido, unicidad incidente+tipo+destino. Tipos incident.opened, incident.recovered, test. Estados pending/sending/sent/failed/expired/cancelled/not_enqueued. No borrado en cascada de historial de rutas eliminadas. Reinicio recupera sending para reintentar; al menos una vez (duplicado posible tras aceptación con respuesta perdida).
- Worker fuera de peticiones/transacciones, orden por chat, >=3s por chat, timeout5s, 5 intentos máx con esperas10/30/120/300s+jitter. Respetar Telegram retry_after en429. Errores permanentes4xx no reintentar, 5xx/timeouts sí. Expirar pendientes a24h. Limitar pendientes/sending a10000; saturación registra not_enqueued sin bloquear incidencia. Resultados terminales retención30d. Duración y causa en avisos, sin credenciales/request payloads.
- Deshabilitación global cancela todos pendientes, por ruta cancela su alcance; pausa/borrado cancela sus pendientes y no envía recuperación administrativa. Cambio destino no redirige lo ya encolado; si operación envío ya aceptada no puede deshacerse.
- Panel settings globales y por backend, prueba, historial paginado de entregas y errores saneados. Estado cola/antigüedad visible.
